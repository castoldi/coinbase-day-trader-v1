# Local Paper Trading Platform Design

Date: 2026-06-14
Status: Approved for implementation planning

## Goal

Build the first milestone of a Coinbase crypto day-trading project as a safe local paper trading platform. The system should connect to Coinbase early for sandbox and market-data integration testing, but it must not place live trades in this milestone.

The first version should provide enough structure to run a bot locally, track simulated account performance from an initial 1000 USD balance, prepare reusable market data and backtests, and expose a dashboard with current trading state.

## Key Decisions

- Use Python for backend trading, backtesting, persistence, email, logging, and Coinbase integration.
- Use FastAPI for a local API consumed by the dashboard.
- Use SQLite for local durable state.
- Use React and Vite for the dashboard.
- Default trading mode is local paper trading.
- Coinbase sandbox integration exists for API smoke tests and adapter validation. It is not treated as true exchange-hosted paper trading because Coinbase Advanced Trade sandbox responses are static/predefined.
- Live trading is out of scope for this milestone and must fail closed if selected.

## Architecture

The project has four main layers:

1. Backend application
   - Loads configuration from `.env`.
   - Exposes FastAPI endpoints for dashboard data, bot status, trades, backtests, account state, and strategy metadata.
   - Owns process health and operational commands.

2. Trading engine
   - Loads one strategy, multiple strategies, or all available strategies from startup arguments.
   - Evaluates market data and creates paper orders.
   - Sends all simulated execution through the local paper broker.
   - Applies account and risk guards before any simulated order.

3. Integration adapters
   - Paper broker records simulated fills and account changes in SQLite.
   - Coinbase adapter supports sandbox/public integration checks, product discovery, and market-data retrieval where available.
   - Future live broker mode is represented only as a blocked configuration path.

4. Dashboard
   - React/Vite app calls the backend API.
   - First screen is a live trading view.
   - Additional pages cover trading history, account management, backtests, and strategies.

## Persistence

SQLite stores:

- Bot heartbeat and health status.
- Account state, including initial equity, current cash, current equity, realized PnL, and trading-enabled flag.
- Open trades and closed trades.
- Strategy registry and active strategy selection.
- Market candles downloaded from Coinbase-compatible sources.
- Backtest runs, summary metrics, period metadata, and per-trade results.
- Safety lock events and manual reset events.

Secrets are never stored in SQLite.

## Configuration And Secrets

Secrets live only in `.env`. A committed `.env.example` documents the expected keys without secret values.

Expected configuration includes:

- Coinbase API key identifiers and private key material.
- Coinbase mode, defaulting to `paper`.
- Gmail SMTP user and app password.
- Email recipient.
- Bot starting capital, defaulting to `1000`.
- Maximum drawdown stop, defaulting to `50%` of initial capital.
- Dashboard and API host/port values.

Email subjects generated by the bot must start with `AI-BOT`.

## Trading Modes

### paper

The default mode. Orders are simulated locally and persisted to SQLite. This is the only mode allowed to execute trades in the first milestone.

### coinbase_sandbox

Used to test Coinbase client configuration, endpoint reachability, response parsing, and integration wiring. It must not be represented as real paper trading with live simulated exchange balances.

### live

Reserved for future work. Selecting this mode must stop startup with a clear error.

## Bot Lifecycle

The bot is started through a script intended to be called every 30 minutes.

Startup behavior:

- Check the last bot heartbeat.
- If an existing bot is healthy, exit without starting another bot.
- If no bot is running or the heartbeat is stale, start a new bot process.
- Record bot status and heartbeat in SQLite.
- Write bot logs to daily rotating files under `logs/`.

The dashboard has its own start script and separate daily rotating logs under `logs/`.

Logs rotate daily, keep 7 days, and compress rolled-over logs.

## Account And Risk Management

The paper account starts with 1000 USD for live bot simulation.

The account rolls forward:

- A 200 USD loss leaves 800 USD for later trading.
- A 300 USD gain leaves 1300 USD for later trading.

If equity falls to 500 USD or below, trading is permanently disabled until a manual local reset command is run. This safety state is stored in SQLite and must survive process restarts.

## Strategies

The platform supports multiple strategies through a stable interface:

- Strategy name and version.
- Required products/timeframes.
- Signal generation from candle data.
- Risk parameters such as stop loss and take profit.
- Metadata for dashboard documentation.

Startup supports:

- A single strategy.
- A comma-separated list of strategies.
- `ALL` to enable every available strategy.

The first strategy is a price-action strategy based on the provided YouTube video. The implementation can scaffold the strategy interface and documentation page first, but final rules require extracting and reviewing the transcript.

## Dashboard

The dashboard should be useful immediately, not a marketing landing page.

Main live view shows:

- Current equity and cash.
- Realized and unrealized PnL.
- Win rate.
- Open trades.
- Closed trades.
- Coins being traded.
- Current coin prices.
- Bot health.
- Active strategies.

Other pages:

- Trading History: searchable/filterable open and closed trade records.
- Account Management: starting capital, current equity, drawdown status, safety lock status, and manual reallow control.
- Backtests: all backtest runs, combined summary, and per-period results.
- Strategies: strategy descriptions, entry logic, stop loss, take profit, and two candle chart examples per strategy.

Dashboard screenshots should be generated after the UI exists and referenced in `README.md`.

## Backtests And Market Data

Market data should be downloaded for main Coinbase USD crypto pairs from 2024 onward and stored in the project so it can be reused. It is acceptable to commit this market data.

Every standard backtest run starts with 1000 USD cash.

Standard backtest periods:

- 2024
- 2025
- 2026
- Last 30 days

Each backtest records:

- Strategy and version.
- Products traded.
- Period.
- Starting cash.
- Ending equity.
- Total return.
- Max drawdown.
- Win rate.
- Number of trades.
- Per-trade details.

The Backtests landing page shows a combined summary across all recorded runs.

## Testing

Backend tests cover:

- Configuration loading and validation.
- Secret-safe example configuration.
- Paper account balance rollover.
- Safety lock at 50% drawdown.
- Manual safety reset command.
- Strategy selection for single, multiple, and `ALL`.
- Coinbase sandbox adapter construction and smoke-test behavior using mocked responses where needed.
- Backtest period bookkeeping.
- Trade persistence.

Dashboard verification covers:

- App starts locally.
- Main dashboard renders without API errors.
- Core metric cards load from backend data.
- Navigation works for trading history, account management, backtests, and strategies.

## Out Of Scope For First Milestone

- Live Coinbase order placement.
- Autonomous real-money trading.
- A complete production-grade strategy before transcript extraction and review.
- Cloud deployment.
- Multi-user authentication.
- Tax reporting.

## Open Implementation Notes

- If the GitHub CLI is authenticated, create and push the public repository directly. If not, stop and ask for authentication or manual repo creation.
- If YouTube transcript access is blocked, document the gap and implement the strategy shell with explicit pending-rule markers for reviewed rules.
- Coinbase API setup instructions must be based on current official Coinbase documentation during implementation.
